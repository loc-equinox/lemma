# Architecture

The optional terminal observes provider events through an independent callback and a bounded in-memory buffer per book. A separate read-only SSE endpoint sends an initial replay and incremental batches every 200 ms only while subscribed; slow observers disconnect rather than blocking the provider. Token deltas never save SQLite snapshots or trigger workspace refreshes. Job start/end timestamps are persistent, while diagnostic transcripts are session-only and Clear invalidates their replay buffer. The adapter records the exact compact turn input, and logs session teaching instructions only beside the actual thread/start or thread/resume request (not on every turn). It also records public message/summary and tool output events; final items replace streamed fragments for display. Notifications are bound to the acknowledged turn ID, and the engine rejects observation callbacks for cancelled or outdated jobs. Protocol fields were checked against installed Codex 0.167.0 bindings and the [official App Server event documentation](https://learn.chatgpt.com/docs/app-server).

Lemma is a local React/TypeScript application served by Express on loopback. SQLite stores a transactional workspace snapshot with WAL and full synchronous writes. Textbook materials remain read-only. The backend can explicitly update the two study-context Markdown files inside a book directory; code, SQLite, logs, and testing artifacts stay outside book directories.

The backend owns reading state. Each tree has its own cursor and cursor epoch; a book has one active tree. Routes contain ordered slots, and explanation routes save a return position at question submission. A route position remains valid before its node exists. Resolving an exhausted explanation route follows its saved return route recursively. Structural parent links are separate from reading successors. Opening a node never calls a progression API.

Questions pause speculation and create a new route. Results never move the reading pane. Explicit “Enter explanation” activates that route; asking on the active node then completes the source step. Continue requires the expected cursor epoch and node, and request IDs deduplicate mutation retries. Resume tree is explicit.

Each book has one serialized generation queue and one persistent Codex thread. Questions cancel speculative work; cancellation is recorded before interrupting the provider. Output must match the job, canvas epoch, route offset, assigned IDs, successors, and eligible revision versions. Late results are ignored. Initial routes request two steps; subsequent work prepares only one successor. An existing return node satisfies the buffer.

Revisions create new immutable node versions in the same route slot; old versions remain inspectable. Completed/current nodes cannot be revised. Viewing a node retains that version even when it is superseded. Startup marks unfinished jobs as failed with an explicit retry action. Graceful shutdown records the same recovery state before aborting providers and closing SQLite.

Codex protocol: newline-delimited JSON-RPC over `codex app-server --listen stdio://`. Installed CLI 0.167.0 bindings were generated and inspected for thread/start, thread/resume, turn/start, turn/interrupt and outputSchema. See https://learn.chatgpt.com/docs/app-server. One subprocess is used per actively connected book, with default installed authentication and model. Threads use read-only sandboxing and never approve mutations. Book AGENTS.md conventions supplement public teaching/structured-output rules.

Defaults: local desktop use, English UI with multilingual mathematical content; explicit directory path entry; no hosted deployment; no automatic retry after a crash. Demo mode is opt-in and visibly labeled. No material contents are uploaded by the application itself; live Codex necessarily sends relevant context to the user's configured model provider.


Model and reasoning choices are book-level preferences, persisted independently of canvas state. `model/list` is paginated; the GUI can refresh its one-minute cache, while generation reuses the last known catalog without expiry-driven discovery; `config/read` resolves local defaults for the material directory. Only the model/effort metadata is exposed to the UI. Each running job captures its settings before generation. The adapter sends explicit `model` and `effort` on every `turn/start`, so restoring defaults cannot accidentally retain a previous turn’s overrides. Settings changes neither interrupt active work nor replace a thread. Legacy workspaces acquire null preferences, retaining their configured Codex defaults.


## Durable study context and reference nodes

Document jobs (`notes`, `progress`) share the per-book serialized generation queue and persistent Codex conversation, interrupting speculative work. They do not create a learning route or move its cursor. Each generation snapshots both study files; document output has a separate schema and is validated against its job and fixed filename. The backend checks the file hash before saving, preserves existing note sections, and records before/after bodies in a SQLite write-ahead journal before atomically replacing the file. Startup can recover the reference and completed job after a file/state commit interruption. Backups survive canvas Clear.

References are a separate entity from `Step`; they have no completed flag, route index, or reading successor. Their source content, chapter key, revision and supersession links are persisted. A new reference version leaves an already displayed old version intact. Questions may target reference IDs and capture the same return cursor as old-step questions. With no active tree, the application creates a question route with a null return destination.

The GUI supports explicit task selection and bounded command recognition (`/notes`, `/progress`, explicit file update requests, and common Chinese summary/progress commands). Ambiguous prose remains a learning prompt; the task selector gives a deterministic way to request document changes. Reference content is read-only in the GUI; document updates are explicit new tasks. Clear never implicitly reimports saved files.


## Compact per-turn context

`context.ts` builds bounded local prompts instead of serializing every node and both study documents into each turn. A learning request includes the tree task, assigned slots, canvas epoch, current reading position, saved return destination, two accepted-node summaries, and a source quotation (at most 6,000 characters) for a question. Revision candidates are summaries of at most eight eligible nodes; remaining candidates and exact versions are available through lookup. Document tasks receive file paths/hashes and current reading information, with the relevant chapter or progress record retrieved on demand. No extra model call generates summaries or retrieves context.

Each running turn has a private temporary `context.json` under the application's context directory (OS temporary directory for standalone providers). This contains the exact job snapshot, all current book entities and study-file snapshots; it is **not** attached or sent as prompt text. Existing read-only shell tools can select individual entries with python3. This also supports compaction recovery and questions about another tree or superseded versions. The installed 0.167.0 resume schema does not accept `dynamicTools`, so file lookup preserves existing threads without adding a new protocol dependency or replacing conversations. Files are removed on success, failure, cancellation and graceful shutdown. An abrupt process kill can leave an orphan temporary directory; it is not loaded as authoritative state.

Teaching instructions now distinguish a partial request from the complete authoritative lookup. Absence from a prompt does not invalidate a node. A new canvas epoch, cancelled/uncommitted output or superseded version still cannot supply valid navigation. Models reuse prior conversation and already-read materials; there is no unconditional reread requirement. Backend validators remain the final authority.

Cold generation uses its own initialized App Server for catalog discovery, then starts/resumes the thread on that process. Warm turns use cached model metadata even after the GUI refresh TTL expires; explicit GUI refresh uses the existing connection when available. `thread/resume` uses `excludeTurns:true`, which suppresses history in the RPC response without discarding model context. Identical progress messages are coalesced before emitting SSE changes. Optional per-job metrics distinguish payload bytes, adapter preparation, submission acknowledgement, first item event, command count and total provider time; the measurements exclude engine work before the adapter and are not token counts.
